# Feeltriva — decision register

Engineering decisions made while implementing the handoff, and the product, clinical and
data decisions that are still open. The open items come from the handoff's own register
(`docs/05_IMPLEMENTATION_BACKLOG.md`); none of them has been decided on anyone's behalf.

## Engineering decisions made

| # | Decision | Why | Revisit when |
|---|---|---|---|
| E1 | One Python distribution (`pyproject.toml` at the root) whose packages live in the monorepo paths from `docs/03` | Keeps the documented layout without a multi-project workspace; one lockfile | A package needs its own release cycle |
| E2 | Python 3.12, dependencies resolved by `uv` and pinned in `uv.lock`; Node dependencies pinned in `apps/web/pnpm-lock.yaml` | Spec requires locked, supported versions | Routine upgrades via Dependabot |
| E3 | Synchronous SQLAlchemy with psycopg 3; FastAPI runs handlers in its thread pool | Simple transactional code; concurrency correctness comes from the database, verified by tests | Measured latency requires async |
| E4 | Migrations are hand-written SQL in Alembic, `0001` copied statement for statement from `specs/schema.sql` | The spec asks for reviewed migrations; autogeneration would hide differences from the reviewed SQL | — |
| E5 | The API connects as `feeltriva_app`, a non-owner, non-superuser role; private tables use forced row-level security keyed on a per-transaction `app.owner_subject` | Ownership holds even if a query forgets its filter; superusers bypass RLS, so the app must not be one | — |
| E6 | Service logic is also unit-tested on in-memory SQLite; the same suite runs on PostgreSQL in CI | Fast feedback without services; PostgreSQL-only guarantees (RLS, row locks, partial unique index) have their own tests | — |
| E7 | Session free text (messages, quoted phrases, idempotent replay bodies) is encrypted with Fernet before storage | Schema specifies encrypted columns; key comes from `SESSION_ENCRYPTION_KEY`, with a built-in non-secret key allowed only in development/test | Managed KMS / key rotation before any live data |
| E8 | Mock bearer tokens (`dev:<subject>`, `dev-reviewer:<name>`) exist only when `AUTH_MODE=mock`, which settings refuse outside development/test | Local use without an identity provider; cannot be enabled in production configuration | Real identity provider chosen |
| E9 | Fixture mode serves one synthetic, nonmedical release (`fx.*` concepts, "Illustrative possibility A") shipped in `packages/clinical` | Exercises escalation, scope, contradiction, missingness and missing evidence without inventing medical rules | A reviewed clinical release exists |
| E10 | Clinical mode refuses to start with the mock extractor, a synthetic bundle or any unapproved item | "Unapproved rules cannot run in clinical mode" enforced at load time, not by convention | — |
| E11 | Urgency and scope rules run on every observation change and use unconfirmed details too; candidates use confirmed details only | FR04: escalation must never wait for confirmation or a questionnaire; explanations must not rest on unconfirmed interpretations | Clinical owner reviews this policy |
| E12 | Fixture results report urgency `not_assessed` unless an escalation rule fires | There is no approved urgency content; `not_assessed` is not "low" | Approved urgency rules exist |
| E13 | A candidate is returned only if every evidence ID it cites resolves; otherwise it is withheld and reported as an unknown | "No evidence, no claim" | — |
| E14 | An answer is accepted only for the question the server would ask now; otherwise 409 | Prevents attaching an old answer to a new question | — |
| E15 | A structured observation for a concept that already has a current observation must supersede it; an observation can be superseded once (database unique index) | Corrections form an auditable chain, never a fork | — |
| E16 | Provider failure during assessment returns 503 and is not stored against the idempotency key | A failure must not become the permanent replay for that key, and must never look like a result | — |
| E17 | Deletion removes messages, observations, answers, assessments and earlier replay bodies in one transaction, keeps a tombstone, and returns `deletion_scheduled`, not `deleted` | No backup, trace or object-store purge exists yet, so completion is not claimed | Retention policy and purge job exist |
| E18 | Missing, deleted and not-owned sessions all return the same 404 | Existence of another caller's session is not disclosed | — |
| E19 | Session lifetime is `SESSION_TTL_MINUTES` (default 1440); expired sessions return 403 `session_expired` and can still be deleted | A technical session timeout, not a data-retention policy | Retention decision |
| E20 | `GET /v1/conditions/{disease_id}` and `/internal/v1/review/*` are additions beyond `specs/openapi.json` | Needed for M2 (review workspace, reviewed-only serving); the supplied contract file is left unchanged | Contract owner extends the OpenAPI |
| E21 | Rate limiting (HTTP 429) is not implemented | Needs the declared pilot load and an infrastructure choice | Before any shared deployment |
| E22 | Web app is Vite + React + TypeScript + Tailwind in `apps/web`, built here from `docs/06_LOVABLE_FRONTEND_PROMPT.md` rather than generated by Lovable | No Lovable output was supplied; the prompt allows any supported React + TypeScript template | Lovable-generated code is supplied |
| E23 | Feature values are stored sparsely: one `case_features` row per cell whose value is not `0`; a `0` is the absence of a row for a registered column, with its meaning kept as `zero_semantics = unknown` on the mapping (supersedes the earlier deferral of the cell-level load) | Measured on 2026-11-16: all 371,234,666 matrix cells are `0` or `1` and only 14,565,013 are `1`. Storing zeros would be 356 million rows and would invite reading an imported zero as an explicit denial, which the handoff forbids | A source with non-binary or blank cells is added |
| E24 | GitHub repository is public (owner's instruction, 2026-11-16; it was created private first) | Owner decision. Raw archives, `.env`, model artifacts and session data are ignored and were never pushed. The tracked `data_audit/` crosswalks and `experiments/results/` are derived from datasets whose origin and licence are still unknown | Data rights are documented; a software licence is chosen |
| E25 | User conversations are stored in Apache Cassandra, not PostgreSQL. **Everything** in a conversation moves: messages, follow-up answers, interpreted observations and corrections, assessments, summaries and replay bodies (owner's instruction and confirmation, 2026-11-16) | Owner decision. Planned as step C; until C is implemented the M3.3 PostgreSQL tables are still in use | — |
| E26 | The product and its models learn, retrain and evolve continuously (owner's instruction, 2026-11-16) | Owner decision. Planned as step L: automated feedback capture, retraining, evaluation gates, shadow/canary promotion, drift-triggered runs | D-L1 below |
| E27 | Two sources of truth, never mixed: **PostgreSQL for data** (datasets, diseases, features, aliases, statements, evidence, rules, releases, review state) and **Cassandra for conversations**. Conversation records refer to PostgreSQL entities by ID and release version only; no entity is defined or edited in Cassandra, and no conversation content is stored in PostgreSQL (owner, 2026-11-16) | Owner decision: "We need a common source of truth for the data that will be Postgres and for the conversations, Cassandra" | — |
| E28 | A new entity discovered by learning from conversations (a new symptom/feature term, alias or disease label) is added to PostgreSQL as a **new record**. Done carefully: status `pending`, de-duplicated against existing records with the same lexical normalisation, written with a provenance row (support count, first/last seen, discovering model version), never containing a user's sentence, session ID or identity, raised only above a minimum-support threshold, never overwriting an approved record, and served only after review and release (owner, 2026-11-16: "Do it very carefully") | Owner decision; safeguards are this project's interpretation of "carefully" and of the handoff's review rules | D-L3 sets the threshold |
| E29 | Model promotion: retraining, evaluation and shadow/canary trials are automatic; a named person approves before a new model's suggestions are shown to real users in clinical mode. Fixture/demo mode stays fully automatic (owner, 2026-11-16) | Owner decision; matches the handoff's release gates | — |
| E30 | **Data origin (owner, 2026-11-16): "These are real data, completely original."** The six archives are treated as real health data owned by the owner | Owner's statement; no written provenance, licence or data-subject consent record has been supplied. Because the data are real, the 50 individual case rows in `experiments/results/failure_examples.csv` in this public repository need the owner's decision (D-P1) | Written provenance is available |
| E31 | **Target users (owner, 2026-11-16): people in India, English text.** Adults, as the handoff proposed | Owner decision | A new population or language is added |
| E32 | **Consent (owner, 2026-11-16): consent is taken from users and implemented in the product** | Owner decision. Planned as M3.16: versioned consent text, acceptance recorded per session, what is kept and for how long stated to the user | D-L2 (is consent to model training required or optional) |
| E33 | **Retention (owner, 2026-11-16): conversations are kept for the last 30 days**, because the model evolves continuously from them | Owner decision. Implemented in step C as a 30-day time-to-live; learning (step L) reads at most the last 30 days. Backup lifetime was not stated; proposed: no backup of conversations older than 30 days | Backup lifetime confirmed |
| E34 | **Feature meanings (owner, 2026-11-16): derive each dataset column's meaning from the supplied data and map accordingly**, instead of waiting for a clinician | Owner decision; replaces the handoff's clinician review for this item. M2.7 becomes a data-derived classification: kind (symptom, sign, history, risk factor, measurement) and zero meaning from the column and question wording and the value patterns, each with its recorded basis; columns the data cannot settle are listed for the owner, not guessed | — |
| E35 | **External case set (owner, 2026-11-16): yes, and the model is also trained on it** | Owner decision. A case used for training cannot also measure the model, so the set is split once: one part for training, one part held out and never trained on. The owner supplies the cases | Cases supplied |
| E36 | **Clinical release gates (owner, 2026-11-16): none; everything goes in a single release.** No staged gates and no pass/fail thresholds | Owner decision; overrides the handoff's clinical gates (`docs/01` §7) and narrows E29 to one go-live decision by the owner. The evaluation of M4.5 is still run and shown to the owner before that decision; the engineering checks (tests, contract, ownership) still apply | — |
| E37 | **Clinical mode (owner, 2026-11-16): it will be enabled** | Owner decision. In code, clinical mode needs a non-synthetic release in which every rule, question, candidate and evidence item is approved, and a non-mock extractor; approvals are recorded under the approver's name. Engineering builds to that; it does not author medical rules or mark content approved by itself | Go-live decision |
| E38 | **Public repository contents (owner, 2026-11-17): keep it.** `experiments/results/failure_examples.csv` (50 individual real cases without identifiers) and the `data_audit/` crosswalks stay public | Owner decision on D-P1 | — |
| E39 | **Urgency rules (owner, 2026-11-17): "Define the urgency rules and implementation, write it from your viewpoint as of now."** The urgency rule set is drafted by the engineering assistant, not by a clinician | Owner decision; replaces the handoff's requirement that a reviewer author this content. Planned as M2.10: a conservative draft built only from widely published emergency warning signs, biased toward escalating, every rule carrying its stated basis, the whole set labelled as an unreviewed draft. It is served only after the owner approves it by name. It is not a validated triage protocol and a doctor's review remains strongly advised | A clinician reviews it |
| E40 | **Evaluation before go-live (owner, 2026-11-17): agreed.** The M4.5 evaluation is shown to the owner before clinical mode is switched on | Owner decision | — |
| E41 | **Columns the data cannot classify are listed for the owner (owner, 2026-11-17): agreed** | Owner decision; see E34 | — |
| E42 | **Brand name (owner, 2026-11-17): Feeltriva.** No clinical owner has been named | Owner decision. The name has not been checked against trademarks, domains or company registers (D-B1) | — |
| E43 | **Brand clearance (owner, 2026-11-17): not needed; the product's name is Feeltriva.** No trademark, domain or company-register check will be done | Owner decision; the owner accepts the risk of a later naming conflict | — |
| E44 | **Harm review (owner, 2026-11-17): reports of bad advice are reviewed by the owner personally for now.** Reference cases with a doctor's answer are agreed in principle | Owner decision. Planned in M6.2 / M6.6: a report channel in the product and a log of every report and the action taken | Cases supplied; another reviewer named |
| E45 | **Scope (owner, 2026-11-17): the product is not going live for now, and is built complete end to end with nothing from the handoff left out** | Owner decision. Every item in `TRACEABILITY.md` is to be built; where conversations are hosted is decided at go-live | Go-live |
| E46 | **Language model (owner, 2026-11-17): the Claude API is used.** User text is sent to Anthropic for extraction and explanation once that is built and configured | Owner decision on the outside-provider question. M5.1 implements the Anthropic adapter; it needs an API key from the owner; the consent text (M3.16) must tell users their text is processed by an outside provider | Key supplied at M5.1 |
| E47 | **Conversation hosting (owner, 2026-11-17): Cassandra is built into this product repository and run as part of the product's own stack**, not a managed service from another company | Owner decision; closes D-R1. Step C defines the Cassandra service, keyspace, schema migrations and configuration in `infra/` of this repository; conversations live wherever that stack is deployed | A deployment location is chosen |

## Open decisions (owner needed)

| Decision | Proposed starting point in the handoff | Needed before |
|---|---|---|
| Age and unsupported populations | Adults; children and pregnancy-specific diagnosis out of scope | Live scope routing |
| Responsible clinical reviewer | Not assigned | Any clinical rule or knowledge approval |
| Brand, domain, trademark | "Feeltriva" working name, not cleared | Public branding |
| Hosting and model vendor | Managed private services, provider-neutral adapter | External health-data processing |
| Budget and load | Measure per-session cost and concurrency | Production sizing, rate limits |
| Commercial offering | Clinic intake SaaS / consumer tracking hypothesis | Customer discovery |
| D-L2 Training consent | Handoff: separate from use consent and off by default; nothing is learned from a session without it. The owner wants learning from user conversations, so the consent wording and default need an explicit decision | L1 |
| D-L3 Entity-discovery threshold and reviewer | Proposed: a candidate is raised only after it appears in a minimum number of distinct consented sessions (number to be set), and a named reviewer approves it | L3a |
| D-C2 Clinical owner | Nobody medically responsible has been named. With E36 (no gates) and E39 (urgency rules drafted by the assistant) there is currently no clinician anywhere in the path to real users | Before clinical mode |
| D-O1 Label origin | How the disease labels in the archives were assigned (clinician diagnosis, self-report, other); cannot be derived from the files | M4.2 |
| Software licence for this repository | None chosen (all rights reserved by default) | Sharing the code |
